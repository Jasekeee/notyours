Prove your users' data stays theirs.

notyours runs your app on localhost, signs in as several users in separate real browsers, and checks whether one user's data ever reaches another user's screen or network traffic. A canary token decides. No AI judges the page.

Install and run the demo

Needs Node 22+, Google Chrome, and kane-cli 0.10.0, logged in. notyours isn't on npm yet, so run it from GitHub:

npx github:Jasekeee/notyours doctor        # checks Node, Chrome, kane-cli and login
npx github:Jasekeee/notyours demo --quick  # one real leak in the bundled demo app, about 5 minutes

Measured on kane-cli 0.10.0: the quick demo took 4 m 48 s and 61.69 Kane credits. Full steps and the credit model are in the README.

Why

OWASP ranks Broken Access Control first in its Top 10:2025. The usual causes are small: a query without where owner_id = ?, a list endpoint that returns every row, a paid page that hides its button but still serves the data.

Unit tests rarely catch these, because they run one user at a time. notyours signs in as several users at once and checks what each one can actually see.

How it works

  map       static scan of Express / Next.js routes  ─▶  draft boundaries
     │
  agent     your coding agent reads the code, writes real boundaries
     │
  run       Kane as Alice ─▶ creates a record containing NY-ALICE-…
            Kane as Bob   ─▶ visits the targets      ◀── live DOM + network capture
     │
  oracle    did NY-ALICE-… reach Bob?  ─▶  LEAK · HELD · HARNESS
     │
  lock      record it; every later check is a 0-credit replay
     │
  report    report.html + report.json  ─▶  leaks go back to your coding agent

Kane CLI drives one Chrome per user. Each owner's record carries a token such as NY-ALICE-K7Q2MZX4P3RA. If that token shows up in another user's page or network responses, it's a leak.

Verdicts

VerdictMeaning
LEAK (visible)The owner's token appeared in the viewer's rendered page.
LEAK (in payload)The token reached the viewer's browser in a network response, even though the page didn't show it.
HELDThe viewer never received the token, and both positive controls passed.
HARNESSA positive control failed, so the probe proves nothing. Never counted as a pass.

The token decides. Kane's own pass/fail is never used as a verdict. run and replay exit 1 on a leak, so they work as a CI gate.

What it catches, and what it doesn't

Measured on the demo app

  • Bob opens Alice's note: LEAK
  • Guest opens notes: HELD
  • Free user gets the Pro export: LEAK
  • Bob sweeps the note list: HELD

Three seeded bugs in a small demo app, kane-cli 0.10.0.

Not covered

  • Anything you didn't write a boundary for
  • CAPTCHA, OAuth-only and SMS logins
  • Tokens inside images and PDFs
  • Database policies (it tests what the running app returns)
  • Hosts other than localhost, unless you allow them

FAQ

Does it need an AI API key?

No. Kane drives the browsers. The verdict comes from the canary token.

Is it a penetration test?

No. It checks isolation boundaries you declare, against your own app, with test accounts you control.

Can a coding agent edit the tests to make them pass?

The guard hook blocks edits to locked boundaries, recordings, results and config. It's a guardrail for a cooperating agent, not a sandbox.
